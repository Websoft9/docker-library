# Application Secret Spec

## Scope

This specification covers startup key handling in current `apps/`, not external service provisioning, database account rotation, or Docker secrets. `variables.json` declares input names; it is not a generation language. Keep the existing `env.secrets` contract and Websoft9 consumer unchanged in this first batch.

The canonical declaration contract is [appstore-release-spec.md](appstore-release-spec.md#L172). The local Websoft9 `initialize_install_secrets()` implementation was checked on 2026-11-05; its rules below are a compatibility snapshot, not a promise that every running server has that version.

## Classification

| Class | Treatment | Examples |
|---|---|---|
| Independent random seed | Declare in `env.secrets`, use a supported template | Session secret, signing seed, supported hex encryption key |
| Platform password | Existing implicit platform handling; no repeated declarations required | `W9_POWER_PASSWORD`, `W9_RCODE` |
| Shared secret or protocol wrapper | Reference a declared seed; do not independently regenerate copies | CKAN encode/decode, `string:${CKAN_API_TOKEN_SECRET}` |
| Structured or derived key | Application-specific generation must produce the whole compatible group | Signed JWT, key pair, checksum, required base64 encoding |
| External credential | Obtain from the provider/user; do not generate a lookalike | Cloud API token, OAuth secret, issued license |
| Unknown candidate | Keep as `needs_review` until source and consumer semantics are verified | A key-like name or commented sample alone is not evidence |

Only the first class belongs in the generic random generator. A JWT signing seed may be random, but a signed JWT is not a random string. An encryption key's valid length/encoding must be checked against the actual application; replacing encoding to satisfy a generic validator is not a fix.

## Current Consumer Contract

- Read names from `env.secrets`; platform password fields present in `.env` are implicit targets.
- Preserve random portion length and character classes; support alphanumeric, hex case, hyphen-separated segments, and fixed `sk-` prefix. At least 12 random characters are required; prefer at least 32 for new signing/session seeds. This is not a per-field strength guarantee.
- Reject dotted JWTs, UUIDs, PEM, padded base64, arbitrary punctuation, ambiguous prefixes and too-short templates. The `secrets` gate mirrors these rules without implementing generation.
- Preserve `$NAME`/`${NAME}` references, including forward/partial references; reject missing/empty/cyclic references and default-expression syntax in secret references. Keep fixed prefixes in a reference wrapper instead of asking the generator to guess them.
- Explicit user settings win, then cached values, then fresh generation. Cache is keyed by instance identity, protected by locks and atomic writes; retrying an installation reuses values. Deleting an instance clears its installation cache.
- Platform passwords use a special generator rather than same-template matching. The current legacy platform password generator uses Python `random`; strengthening it is downstream work, not implemented here.
- Existing values must not be silently rotated during startup, recreation, upgrade or restore. Cached values and instance `.env` require backup. Restoring an app is not permission to replace encryption/signing keys.
- The generic generator has no JWT signing, pair derivation or shared-literal inference. Equal defaults in two declarations do not establish a dependency.

## CKAN First-Batch Fix

Declare only two independent random templates: `CKAN___BEAKER__SESSION__SECRET` and `CKAN_API_TOKEN_SECRET`. Preserve CKAN's protocol wrapper and share the seed:

```dotenv
CKAN___API_TOKEN__JWT__ENCODE__SECRET=string:${CKAN_API_TOKEN_SECRET}
CKAN___API_TOKEN__JWT__DECODE__SECRET=${CKAN___API_TOKEN__JWT__ENCODE__SECRET}
```

Websoft9 can generate the seed without changing `string:` or separating signing and verification. Direct Compose uses the supplied shape templates and does not automatically provision production secrets. Existing installations must retain their own key values; replacing templates is not automatic key rotation. Changing session/JWT keys may invalidate existing sessions/tokens.

## Coverage Inventory

`metadata/secret-coverage.json` is generated by `libs.secret_audit` and checked for drift in CI. It includes all 143 current app metadata files, excludes archives, and stores only variable names, reference names, configured service names and result flags, never defaults or generated values.

| `no_candidates_in_source` | 40 | No candidate found in scanned inputs; not a manual proof of no secrets |

Eight apps explicitly declare `env.secrets`; some also remain `review_required`. Seven now pass template generation after the CKAN fix, and Semaphore UI remains blocked. These are not deployment or application-authorization verdicts.

The scan examines active `.env` keys and Compose environment names/wiring. `configured_services` means a value is supplied by Compose, not that the image actually consumes it. It cannot inspect image-internal defaults, provider ownership, cryptographic relations or arbitrary generated configuration. Unmanaged key-like names are deliberately unclassified; blank fields are not automatically harmless. Full human/source review of the 20 candidate apps is follow-up work, not claimed complete by this first batch.

Rebuild after changing inputs, declarations or wiring:

```bash
PYTHONPATH="$PWD/cli" .venv/bin/python -m libs.secret_audit --output metadata/secret-coverage.json
PYTHONPATH="$PWD/cli" .venv/bin/libs app-check --app ckan --gate secrets --json
```

## Acceptance

1. Validate schema, existing policy, supported literal templates and references. Newly changed secret inputs must pass the separate `secrets` gate; the legacy aggregate gates do not imply generation compatibility.
2. Test the real consumer on temporary copies: correct formats, shared/prefixed values, retry stability, different-instance uniqueness, and no secret output. No external checkout is required for `make test`.
3. Deploy only changed runnable behavior, remotely when configured. Verify initialization, health, logs, actual authenticated use and retained data/keys; HTTP 200 alone is insufficient for key correctness.
4. Keep real instance values during upgrades/restores. Validate any rotation using the app-specific procedure separately; no generic regenerate-all feature is introduced.
5. Owner validates login and a relevant business path. Static metadata, generated samples and automated deployment do not replace Owner E2E.

## Deferred Work

- Semaphore UI: `SEMAPHORE_ACCESS_KEY_ENCRYPTION` requires a padded-base64-compatible strategy; current declaration is incompatible. Do not convert it to arbitrary alphanumeric text or suppress the gate failure.
- Supabase: currently uses public HS256 demo `JWT_SECRET`/`ANON_KEY`/`SERVICE_ROLE_KEY`; no group-generation implementation. Select and validate application-specific signing/persistence before implementation; do not declare three independent random values.
- Other unclassified inventory candidates: verify upstream format, external ownership, actual consumers and initialization/rotation semantics before deciding to declare or exclude.
- Websoft9 generator changes, shared packaging libraries and downstream edits are not authorized by this batch. No real production key rotation is performed.
